# [CW-0036] [bug] 二重起動防止のTCP固定ポートがWindows動的除外ポートと競合し「Already Running」と誤判定されて起動できない

## 概要

アプリケーション起動時、多重起動していないにもかかわらず「Clip Watcher is already running.」というダイアログが表示され、起動に失敗（即時終了）する現象が発生します。

## 事象 / 発生状況

- スタートアップ（`ClipWatcher.bat`）または手動起動時に「Clip Watcher is already running.」と表示され終了する。
- タスクマネージャーや `netstat` を確認しても、ClipWatcher のプロセスや当該ポートをリッスンしている別アプリケーションは存在しない。

## 原因 (Root Cause)

1. `src/event_handlers/__init__.py` 内の `start_app()` で、単一インスタンス制御（二重起動防止）のために TCP ポート `61957` への `socket.bind()` を行っている。
2. Windows（Hyper-V / WSL2 / WinNAT等）が動的に確保する「ポート除外範囲（Excluded Port Range）」に、ポート `61957`（範囲: `61883 - 61982`）が含まれている。
3. これにより、ポートが未使用であっても OS 側から `WSAEACCES` (10013: 権限のないソケットアクセス) が返され、`except OSError:` で二重起動と誤認されて `sys.exit(0)` される。

## 期待する動作

- 他のインスタンスが起動していない場合は、OSの除外ポート設定等の影響を受けずに正常に起動できること。
- 二重起動防止がネットワークスタックの状態（Hyper-V / WSL の予約等）に左右されず堅牢に機能すること。

## 実際の動作

- ポート `61957` が Windows の動的除外ポート範囲に含まれている環境において、未起動にもかかわらず二重起動と判定されて起動できない。

## 関連箇所

- `src/event_handlers/__init__.py` : `start_app()` 内のソケットバインドロジック
- `doc/archive/INVESTIGATION_QUICK_TASK_AND_MULTI_INSTANCE.md` : 多重起動制御の調査仕様書

## 修正案

### 案1: Windows Named Mutex 方式への移行（推奨）
TCP ポートを使用せず、Windows カーネルの Named Mutex（名前付きミューテックス）を使用してインスタンス判定を行う。ポート衝突や除外ポートの影響を根本的に排除可能。

```python
import ctypes
from ctypes import wintypes

ERROR_ALREADY_EXISTS = 183
mutex = ctypes.windll.kernel32.CreateMutexW(None, False, "Local\\ClipWatcher_SingleInstance_Mutex")
if ctypes.windll.kernel32.GetLastError() == ERROR_ALREADY_EXISTS:
    messagebox.showinfo("Already Running", "Clip Watcher is already running.")
    sys.exit(0)
```

### 案2: 除外ポートになりにくいポート帯への変更 / エラーコード判別
- エフェメラルポート帯（49152〜65535）を避け、登録済みポート帯（49152未満の空きポート）に変更する。
- かつ、`OSError` の `errno` が `EADDRINUSE` (10048) 以外のアクセス拒否等の場合はログ出力してフォールバックする等、判定を厳密化する。

## 受け入れ条件

- [ ] ポート除外範囲（Excluded Port Range）に該当ポートが含まれる環境でも正常に単一インスタンスが起動できること
- [ ] 実際にアプリケーションが起動中の状態で2つ目を起動しようとした場合は、正しく「Already Running」が検知されて重複起動が防止されること
- [ ] Windows 以外のプラットフォーム（Linux/macOS等）を将来考慮する場合も壊れない設計であること
