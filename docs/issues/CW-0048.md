# [CW-0048] [security] history_dao における検索クエリのLIKEメタ文字未エスケープによる意図しない履歴露出とDoSリスク

## 0. メタ情報 (Scope & Impact)
- **検出テーマ**: セキュリティ
- **重要度**: Medium
- **関連Issue**: 該当なし
- **起票ステータス**: `stage:ideation` (agys 自律レビュー起票)

## 1. 概要・背景
クリップボード履歴検索においてユーザー入力のLIKE特殊文字（%、_）がエスケープされずにバインドされており、意図しないデータ抽出やパフォーマンス劣化を招く。

### 課題詳細 (Problem Detail)
ClipboardHistoryDAO.get_items において、引数 query が指定された際に params.append(f'%{query}%') としてパラメータ化クエリに渡されていますが、SQLiteの LIKE 演算子におけるパターン文字（ワイルドカード文字 '%' や '_'）に対するエスケープ処理が行われておらず、SQL側での ESCAPE 句も指定されていません。これにより、ユーザーが記号を含む文字列（パスワードやURL、プログラムコードなど）を検索した際に意図しないワイルドカード評価が行われ、本来ヒットすべきでない機密履歴項目が抽出・露出するリスクがあります。また、大量データ環境下でワイルドカードが連続した検索クエリが実行された場合、インデックスが無効化されて過剰な全表パターンマッチングが走り、CPU枯渇やGUIスレッドのフリーズ（DoS）を招く恐れがあります。

- [ ] **案 1 (推奨)**: 案1（推奨）: 検索クエリ内のエスケープ対象文字（例: '/'）およびワイルドカード（'%', '_'）を事前にエスケープする関数を用意し、SQL文を WHERE content LIKE ? ESCAPE '/' と指定してパラメータをバインドします。
- [ ] **案 2**: 案2（代替）: 単純な部分一致検索であれば LIKE 句の代わりに SQLite の組み込み関数 instr(content, ?) > 0 を採用します。これによりパターン文字のエスケープを考慮する必要がなくなり、高速かつ確実にリテラル部分一致を実行できます。
